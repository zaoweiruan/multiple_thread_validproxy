## 2. 技术评审

### 2.1 ✅ 优势

1. **向后兼容**：ParentTemplate 为空时行为不变，旧模板无需迁移
2. **渐进式实施**：可先改 Pool 模板，验证后再推广到其他模式
3. **深度合并策略**：对象递归、数组追加、标量覆盖，语义清晰
4. **数据库变更简单**：仅添加 1 个字段，迁移风险低

### 2.2 ⚠️ 需要澄清的问题

#### Q1: DNS 配置差异如何处理？

**现状**：
- Standalone DNS: 单服务器简化版 `{"servers": ["https://cloudflare-dns.com/dns-query"]}`
- Pool DNS: 多服务器完整版（含 local_local, remote_dns, direct_dns）

**问题**：如果 Pool 继承 Standalone，DNS 配置会冲突。当前方案未明确如何处理。

**建议**：
- 方案 A：Pool 模板包含完整 DNS 配置（覆盖父模板）
- 方案 B：将 DNS 配置从模板中移除，由 ConfigBuilder 动态生成
- 方案 C：创建独立的 DNS 片段模板

**推荐**：方案 B（与 inbounds/outbounds 一致，由代码生成）

#### Q2: 数组去重策略？

**问题**：routing.rules 数组合并时，如果父模板和子模板有相同规则，是否去重？

**示例**：
```json
// 父模板 rules
[{"type": "field", "port": "443", "network": "udp", "outboundTag": "block"}]

// 子模板 rules（重复）
[{"type": "field", "port": "443", "network": "udp", "outboundTag": "block"}]

// 合并结果？
// A: 保留两条（不去重）
// B: 保留一条（去重）
```

**建议**：默认不去重（保留所有元素），避免误删。可在 ConfigVariables 中添加 `dedupeRules` 选项。

#### Q3: 循环引用检测？

**问题**：如果模板 A 继承 B，B 继承 A，会导致无限递归。

**建议**：
- 添加最大递归深度限制（建议 10 层）
- 添加已访问模板集合检测循环引用
- 超出限制时返回错误，记录日志

#### Q4: 父模板不存在时的行为？

**问题**：如果子模板指定了 ParentTemplate，但父模板不存在或已禁用？

**当前方案**：`if (parent.is_object())` 检查，但无明确错误处理。

**建议**：
- 记录 WARN 日志
- 仅使用子模板配置（降级行为）
- 或抛出异常（严格模式）

## 3. 架构评审

### 3.1 与现有架构的一致性

**✅ 一致的地方**：
- 使用现有 `FullConfigTemplateItem` 表，无需新建表
- 复用现有 `FullConfigTemplateDAO`，仅添加字段
- ConfigBuilder 内部改造，不改变外部接口

**⚠️ 潜在冲突**：
- `ConfigBuilder::loadTemplate()` 当前是 private 方法，需要改为可递归调用
- 当前 `loadTemplate()` 返回 `boost::json::value`，深度合并需要引用传递

### 3.2 与项目规范的一致性

| 规范 | 符合要求 | 说明 |
|------|----------|------|
| C++17（禁用 auto） | ✅ | 示例代码使用显式类型 |
| 文档先行 | ✅ | 先写 Spec 再实施 |
| TDD | ⚠️ | 测试计划完整，但未明确 RED→GREEN 流程 |
| PowerShell 语法 | ✅ | 无 Windows 特定命令 |

### 3.3 与已归档规范的关系

**`2026-08-31-Spec-ConfigGenerationPathways`**（已归档）建议"收敛为统一配置构造器"。

**本方案符合该方向**：模板继承是统一构造器的组成部分，进一步收敛配置生成逻辑。

## 7. 实施建议

### 7.1 实施顺序建议

**推荐顺序**：
1. P1: 数据库迁移（添加 ParentTemplate 字段）
2. P2: DAO 扩展（新增字段 + 种子更新）
3. P3: 单元测试（合并逻辑）— **先写测试**
4. P4: ConfigBuilder 改造（loadTemplate + deepMerge）
5. P5: 模板简化（Pool 模板只保留独有部分）
6. P6: 集成测试 + 回归测试
7. P7: 文档更新

**理由**：先写单元测试（P3 提前），确保合并逻辑正确后再改造 ConfigBuilder。

### 7.2 风险缓解措施

2. **灰度发布**：先改 Pool 模板，验证后再推广
3. **功能开关**：考虑添加 `use_template_inheritance` 配置开关
4. **日志增强**：合并时记录详细日志，便于调试
