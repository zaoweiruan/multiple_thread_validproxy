## 2. 阻断项（必须修订后才能进入实现）

### B1. 归因未区分「SIP001 路径 vs 直连 `@` 路径」——P0-B 才是承重墙，P0-A 是补强（3/3 命中）

文档 §3.2/§4 把 `{"add"`/`{"v"` 垃圾节点的成因**单一归因**于 SIP001 分支（R1），并把 method 校验（R2）标为"共犯"。这**漏掉了第二条产出路径**：

| 路径 | 触发条件 | 产出 |
|---|---|---|
| **A（SIP001）** | 行无字面量 `@`：`ss://<base64(JSON)>` ⇒ 走 `:469-482` 解码整段 | `method='{"add'` |
| **B（直连）** | 行含字面量 `@`：`ss://<base64(JSON)>@<host>:<port>` ⇒ `:461` 命中 ⇒ `userInfo=base64(JSON)` ⇒ `:608` 解码 | `method='{"add'`，**且 address/port 是真实公网值** |

- **P0-A（JSON 闸门）只覆盖路径 A**；路径 B 完全不受影响。
- **P0-B（method 形态校验）同时覆盖 A 与 B** —— 因此 **P0-B 是承重墙，P0-A 是补强**。文档把两者并列为"主修/共犯"的表述会在评审与实现中被误读为"P0-A 已足够"。
- 路径 B 若存在，其危害**更大**：产出的是「可投递的公网 address + 合法 port + 垃圾 security」节点，比路径 A 的垃圾 address 更难在下游被拦。

**量化（本轮新增）**：对 `temp/argh94_ss.txt` 的 8163 个产出节点，P0-B 精确剔除 **4261 个（52.2%）**：
`{"add"` 3025 + `{"v"` 1232 + `{"type"` 2 + `{"id"` 1 + `{"seed"` 1；同时对 **3014 个合法形态节点零误伤**（`aes-256-gcm` 1517 / `chacha20-ietf-poly1305` 1261 / `aes-128-gcm` 138 / `2022-blake3-*` 54 / `none` 25 / `chacha20-poly1305` 11）。`3014 + 830(形态合法但白名单外) + 4261(垃圾) + 58(null) = 8163` 完全闭合。

**修法**：
1. 在 `temp/replica_parser.py` 增设计数器，对每个产出节点标注其来自路径 A 还是路径 B，输出拆分实数；
2. §3.2/§4 按拆分实数改写，明确「P0-B = 承重修复（覆盖 A+B）；P0-A = SIP001 语义收紧（覆盖 A）」；
3. 验证计划补路径 B 用例（见 B8）。

### B2. P0-C「404 短路」未定位调用点，且存在行为变更风险（2/3 命中）

§6 P0-C 仅写"在订阅更新流程中……在调用 `parse()` 之前 return"。**未指明函数/文件/行**，不可直接实现；更关键的是——`726599d` 的 404 识别带有**加速器三分支谓词**（`isGitHubHostedUrl` + accelerator-only 时的例外）。若 P0-C 简化为裸 `httpStatus == 404`，则对「加速器托管的 404（非权威）」会**错误短路**，改变既有语义。

**修法**：
1. 定位精确调用点（预期为 `SubitemUpdaterV2::doUpdateSubscription` 中 `fetchUrl` 成功之后、`parser->parse` 之前），在文档中给出函数名 + 行号；
2. 明确 **复用与 `726599d` 完全相同的 404 权威性谓词**，不得新造判断；
3. 补一条 TDD：加速器 404（非权威）时仍执行 parse。

### B3. H4「证伪」的论证方法无效（3/3 命中）

§5 H4 行写「本轮**未证实**（复刻用标准字母表即对齐生产数字）」。**该论证是非逻辑推论**：复刻与生产数字对齐，只证明「复刻忠实于现有代码」，**不能**证明「代码不存在 base64url 缺陷」——若两边都对 url-safe 载荷做同样的静默错解，数字**必然**仍然对齐。

正确的降优先级依据是 **`2026-10-16` 可观测性 P0 的实测**：malformed 集合中 `-`/`_` 出现次数为 **0**（见 `docs/bugfix/2026-10-16-Bugfix-SubscriptionParser-Observability-P0-v1.0.md`）。**必须改引此证据**，并把 H4 从"证伪"改为"**未证实、已降优先级、待真实 base64url 载荷实证**"。

> 连带：`docs/plans/project-plans-tracker.md` 与 `docs/context.md` 中登记的「H4（base64url）证伪」措辞须同步订正。

### B4. H5 未定位根因即给 defense-in-depth（2/3 命中）

H5 = `注入xray outbound 错误: ... Unsupported cipher`（1 次），文档直接给 P1-B「注入前复验」。但**未解释它如何绕过 `isValidProxy` 的 `isSupportedSsCipher` 闸门**。候选根因互斥且处置不同：

- (a) **存量数据**：`2026-08-11` 白名单新增第 9 项之前入库的旧行；
- (b) **旁路插入**：`ShareLink` 导入 / `-S sync` / `-IS import` 等未过 `isValidProxy` 的路径；
- (c) **能力漂移**：白名单与 Xray 实际能力不一致。

**修法**：该日志行携带 `indexId`，**先据其回溯该行的 subid/来源**，判定 (a)/(b)/(c) 后再决定 P1-B 的落点（若为 (a)，只需存量清洗即可，P1-B 可能不必要）。P1-B 保留为下游安全网，但须重述为「定位旁路根因之后的加固」。

### B5. 严重度无量化——垃圾节点真实存活量未知（2/3 命中）

文档断言危害，但**未给出「多少垃圾节点真正入库/存活」**。反证：复刻单订阅产出 8163 垃圾节点，而**全日志**仅 ~1058 条 `unsupported cipher` WARN + 1510 条 `invalid UUID` WARN —— 说明绝大多数垃圾在 `checkRequired()`（`LogLevel::INFO`，本日志不可见）或 Deduplicator 阶段已被丢弃。**若存活量极低，本修复的优先级需相应下调**，不应以 8163 的数字暗示严重度。

**修法**：在实施前做一次只读测量，给出实数后再定级。建议（任选其一）：
```powershell
# 只读打开生产库副本
sqlite3 ... "SELECT COUNT(*) FROM ProfileItem WHERE ConfigType='3' AND (Security LIKE '{%' OR Security LIKE '[%');"
```
或临时在 `insertSubItem` 计数。将实数写入 §1.4「影响量化」。

### B6. P1-A 严重度错标（3/3 命中）

P1-A（误挂 VMess 重新路由）被标为"**可选**"，但按复刻数据它是**单订阅可回收约 4257 个真实节点**的**最高价值项**；同时它是 **P0-B 不丢数据的补偿**——没有 P1-A，P0-B 会把 4261 行"正确但浪费地"记为 malformed 丢弃。

文档 §6 P1-A 已隐含这一点（"回收约 4257 个节点"），却又在建议中降级，属**自相矛盾**。

**修法**：重排为「P0-B（承重，必须）/ P1-A（高价值，建议紧随）/ P0-A（语义收紧）/ P0-C / P2」，并显式写出 P0-B↔P1-A 的「拒绝 vs 回收」关系。P1-A 另需补一条独立风险门：仅当解码结果是**合法 VMess JSON（含 `add`/`id`）**时才改路由，避免"改路由后仍产出垃圾"。

### B7. P0-B 是「弱形态门」，须显式声明与白名单的分层关系（2/3 命中）

`^[a-z0-9._-]{1,32}$` 是**形态门，不是白名单门**：`aaaa`、`null`（58 例）都能通过形态门，仍需 `isValidProxy` 的 `isSupportedSsCipher` 兜底才能拒。文档 §6 P0-B 未言明这一分层，读者可能误以为 P0-B 即可拒净。

**修法**：在 §6.0 原则或 P0-B 处补一句分层说明：「形态门只排除结构性垃圾（`{`/`"`/空格/超长）；cipher 合法性仍由 `isValidProxy` 白名单负责，二者是 defense-in-depth，不可相互替代」。另：`_`/`.` 在真实 cipher 中从未出现，纳入字母表仅为无害冗余，宜注释说明。
